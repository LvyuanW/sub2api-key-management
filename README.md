# sub2api Key 管理

独立的中文管理页，不修改 sub2api 的源代码、二进制和前端资源。用户、余额、并发和分组使用官方管理员 API；官方缺少的指定用户 Key 创建、有效期和启停操作由隔离的数据库适配器完成。

每个 Key 对应一个独立的原生普通用户，由创建它的管理员统一管理。当前按 **sub2api v0.2.17** 的接口实现。

## 数据模型

| 页面操作 | 实际操作 |
| --- | --- |
| 批量创建 | 每项创建独立用户及其唯一 Key |
| 初始额度 | 独立用户的初始钱包余额（USD） |
| 增加 / 扣减 / 设置余额 | 官方管理员余额调整接口；不重置用量记录 |
| Key 并发 | 修改其承载用户的原生并发上限 |
| 分组 | 官方管理员 Key 分组接口 |
| 有效期 / 启停 | 适配器仅更新托管 Key 对应字段，并刷新原生鉴权缓存 |

Key 自身的总额度固定为 `quota=0`（不另设限制），计费由独立用户的钱包执行。这样只有一套实际余额，之前部署的 Key 查询页也能直接读取它。充值不会修改 Key 的有效期、分组或历史消耗。

管理员主账号的余额不与承载用户混用，也不会在创建 Key 时自动扣减。创建初始余额属于原生管理员授予额度的行为。

仅显示启用的钱包计费分组；订阅分组涉及套餐授权和周期额度，当前不使用此模型。默认每批 1–100 项、并发 1–10000。遇到主站限流会等待重试，遇到中断可继续同一批次。

## 管理员登录

- `admin.tmallmodels.com` 嵌入 `tmallmodels.com/__keymgr/frame`。
- `admin.manyai.icu` 嵌入 `manyai.icu/__keymgr/frame`。
- 同源子页面逐次读取主站当前的 `auth_token`；每次操作由服务调用官方 `/api/v1/auth/me` 验证有效管理员。
- Token 不传给 admin 域名的父页面，也不存入本服务的状态文件。
- 主站退出登录或更换登录身份时立即清空界面；服务没有额外的管理员密码和登录会话。
- 没有登录时可打开通用登录提示外壳，管理面板和数据接口均拒绝访问。普通用户登录也不能加载管理面板。

两个主域名的登录状态按浏览器来源隔离。在对应主域名登录，再打开对应的 admin 域名；若未登录，页面提供主站登录入口。

## 前置条件

**可以保持仅后台模式开启、用户注册关闭。** 生产配置不登录普通承载用户，不依赖普通用户自助 Key 接口，也不需要放开其登录验证码或权限。

主站管理员需要先完成官方使用声明确认。服务不会代替管理员确认声明。

本服务会建立 `km-<随机标识>@keymgr.invalid` 的承载账号；密码通过 root 专属主密钥和每项随机标识派生，不向页面返回，不发送邮件。生产配置不获取这些用户的 JWT，管理员身份每次实时校验。

请保持这些账号每用户一个 Key；不要在主站更改托管账号的邮箱、角色、标识备注或替换其 Key。服务会核对身份和唯一 Key，对不一致记录停止自动操作，以免影响错误的余额或并发。

## 独立 Key 适配器

v0.2.17 的管理员接口能管理用户，但没有创建其他用户 Key、修改其过期时间和启停状态的接口。生产配置使用 `key_store.py` 补齐这部分，仍然保留后台模式。

- 使用单独的 PostgreSQL 角色 `key_management_keys`，按 `db-grants.sql` 授权。
- 直接业务写入只涉及托管用户的 `api_keys`：创建记录，后续只更新名称、启停、有效期和更新时间。项目已有的迁移 184 触发器会在相关字段变更时向原生 `auth_cache_invalidation_outbox` 写入 Key 的 SHA-256 摘要；专用角色仅补充该列的 INSERT 和队列序列 USAGE 权限，不读取、修改或删除队列记录，也不改动项目表结构、函数或触发器。
- 不写 `users.balance`、并发、额度计数、用量或任何计费记录；这些仍走原生管理员接口。
- SQL 使用参数绑定，并同时核对用户 ID、邮箱、托管备注、角色、Key ID 和完整凭据，拒绝修改其他用户的 Key。数据库授权按列收窄；托管用户的归属边界由适配器校验实现，并非数据库行级权限策略。
- Key 元数据提交后，清理对应的 Redis 二级鉴权缓存，并发布原生 `auth:cache:invalidate` 消息。消息发送成功不等于订阅进程已经完成清理，因此管理服务随后调用官方管理员接口重新绑定同一分组，让当前 sub2api 进程同步清除对应的一级正缓存和负缓存；该步骤成功后才记录 Key 操作完成并继续余额调整。
- Redis 专用角色只能对 `apikey:auth:*` 执行 DEL，并向这一失效频道发布消息，不能修改其他数据。
- 创建用户和授予初始余额之前，以只读查询检查数据库必填列、所需列和序列权限，包括原生失效队列触发器所需的权限。Redis 预检先 PING，再使用每次随机生成、并非真实 API Key 的哨兵摘要，实际执行限定命名空间内的 DEL/PUBLISH，以验证连接、命令和频道权限；不试写业务行，也不影响现有用户凭据。正式缓存操作和官方同步清理步骤仍需成功。无法完成时保留步骤状态，重试原操作不会重建用户或重复授予余额。

当前部署只有一个 sub2api 进程，官方同步清理调用指向该进程。扩展为多个实例时，应另行验证各实例的缓存失效完成条件，不能将一次 Redis 发布视为所有实例均已同步。

升级 sub2api 后需核对表结构、原生触发器及鉴权缓存协议。批量创建前的结构检查会拒绝不兼容的必填列，不会改表或执行项目迁移。

## 重试与资金安全

批次编号及每项阶段先写入本服务的独立状态文件。用户已创建但响应丢失时，以随机邮箱及托管标识找回原用户，避免再次创建和再次授予初始余额。Key 使用稳定凭据和数据库唯一约束恢复，不重复插入。

余额变更在本地持久化操作编号，并传给官方幂等接口。重复点击或相同请求重试不会重复充值。若余额请求出现无法判断是否已提交的网络错误，服务会锁住该操作，要求先在主站核对记录，避免盲目再次扣款或充值。

原生余额接口只接受正数金额。清零会读取当时余额并通过原子增减归零；如果同时发生消费导致原操作不能安全完成，会返回错误，不覆盖新的消费结果。设为指定非零余额表示明确覆盖当前剩余额度，请按实际意图选择。

没有一个跨用户、Key、余额的上游事务。多字段操作可能部分完成；阶段记录会让同编号重试从未完成步骤继续。大批次受主站请求频率限制时自动等待；关闭页面不会删除已成功创建的数据。未完成批次可从页面继续。

## 构建与运行

主程序只依赖 Go 标准库，Go 1.23+。数据库适配器使用宿主机 Python 3.10+、`python3-psycopg2` 和 `python3-redis`：

```bash
go test -race ./...
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -ldflags='-s -w' -o key-management .
```

生产目录：

- 程序：`/opt/sub2api-key-management/key-management`
- 适配器：`/opt/sub2api-key-management/key_store.py`（root 所有，普通请求不能修改）
- 配置：`/etc/sub2api-key-management/service.env`（root:root，0600）
- 独立状态：`/var/lib/sub2api-key-management/state.json`（0600）
- systemd：`key-management.service`，以 root 运行，监听 `127.0.0.1:8091`

复制 `.env.example` 后填入固定主密钥（`openssl rand -hex 32`）。**主密钥不能丢失或随意替换**：它用于恢复承载账号凭据和 Key。状态文件和主密钥必须一起备份、一起恢复。

配置 `KEY_MANAGEMENT_KEY_HELPER`、专用 `KEY_MANAGEMENT_PG_DSN` 和 `KEY_MANAGEMENT_REDIS_*` 凭据；真实凭据仅放在 root 可读的环境文件，不提交到 Git。按 `db-grants.sql` 创建专用角色并授予列权限。不要使用 PostgreSQL 或 Redis 管理员账号作为运行凭据。

Nginx 为两个 admin 域名反向代理到本服务；两个主域名仅将 `/__keymgr/` 前缀代理到本服务，其余路径继续访问原有 sub2api。子页面的 `frame-ancestors` 精确允许对应 admin 域名，不能添加 `X-Frame-Options: DENY/SAMEORIGIN`。

反向代理必须覆盖 `Host`、`X-Real-IP` 和 `X-Forwarded-Proto`，关闭管理路径的访问日志和请求体记录。API Key 搜索使用 POST 请求体，不放进 URL。

```bash
systemctl status key-management
journalctl -u key-management -n 100 --no-pager
systemctl restart key-management
curl -fsS http://127.0.0.1:8091/healthz
```

原有 `sub2api-backup.timer` 的备份范围包括本服务状态、主密钥、systemd 和 Nginx 配置。恢复时先停止管理服务，恢复匹配的 sub2api 数据库及本服务状态后再启动；不要将不同服务器或不同快照的资源映射混用。

本服务升级只需替换自己的程序并重启。sub2api 网页更新仍然使用其原有机制；升级后应验证管理员、用户、Key 和余额 API 的兼容性。

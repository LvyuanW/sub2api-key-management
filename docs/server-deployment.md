# 生产部署

验证日期：2026-10-20。服务器 `8.209.241.20`，sub2api `v0.2.17`。

## 入口与权限

- `https://admin.tmallmodels.com` 使用 `https://tmallmodels.com` 的管理员登录状态。
- `https://admin.manyai.icu` 使用 `https://manyai.icu` 的管理员登录状态。

先在对应主站登录管理员，再打开管理入口。未登录时只显示登录提示；面板、数据和操作接口逐次验证有效管理员，主站退出后清空面板。

`backend_mode_enabled=true`、`registration_enabled=false`，未放开普通用户登录。没有修改 sub2api 的源码、二进制、前端资源或数据库结构。

## 数据与服务

每个 Key 对应一个独立普通用户。初始额度和余额调整使用原生用户钱包，Key 的总额度固定为 `0`，不另加上限。并发设置对应承载用户的原生并发上限。

用户、余额、并发及分组走官方管理员接口。Key 创建、名称、有效期和启停由专用适配器补齐；数据库角色没有钱包、并发和消耗计数写入权限。原生触发器需要的缓存失效队列仅授予散列值列的插入权限。缓存通过原生 Redis 协议刷新，并调用官方同分组更新作为本机 L1 缓存清理屏障。

| 项目 | 位置 |
| --- | --- |
| 主程序与适配器 | `/opt/sub2api-key-management` |
| root 专属配置 | `/etc/sub2api-key-management/service.env` |
| 管理映射与幂等状态 | `/var/lib/sub2api-key-management/state.json` |
| systemd 服务 | `key-management.service` |
| 本机监听 | `127.0.0.1:8091` |
| 数据库及 Redis 专用角色 | `key_management_keys` |

配置和状态文件权限为 `0600`，服务按要求以 root 运行。反向代理和 HTTPS 证书覆盖两个 admin 域名，证书自动续期。

原有 `sub2api-backup.timer` 每日备份数据库、角色和相关服务配置；已加入本服务的状态及固定主密钥。恢复时必须使用同一快照的数据库、状态和主密钥。不能只替换或丢弃主密钥。

## 已验证

- 两项批量创建产生不同的承载用户和 Key，余额与并发隔离；重复原批次返回相同资源。
- 官方钱包增加、扣减、设为指定值和清零；相同操作编号重试没有重复入账。
- Key 停用后立即拒绝鉴权，恢复后立即通过；过去的有效期阻止请求，清空有效期恢复无限期。
- 修改分组与承载用户并发，另一个 Key 的余额保持原值。
- 两个已有公开查询域名显示各自独立钱包余额。
- 未登录、跨来源请求、非托管 Key 被拒绝；普通用户仍受仅后台模式限制。
- 实际数据库权限拒绝读取密码哈希及修改钱包、并发、Key 额度和消耗计数、删除 Key；Redis 拒绝读取 Key 及访问其他键和频道。

验证未发起收费模型请求。临时用户和分组已通过官方管理员接口删除，临时批次映射随后定向清理。

## 升级

本服务更新自己的程序和适配器后重启 `key-management.service`。sub2api 可继续使用原有网页更新机制。升级 sub2api 后，应核对管理员 API、数据库必填列、原生缓存触发器和缓存失效协议；适配器会在创建用户和授予初始余额前检查当前结构和权限。
